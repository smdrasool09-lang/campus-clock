# College Timetable Management System

A complete frontend prototype of a College Timetable Management System for
**Joy University — School of Computational Intelligence**, built with
**HTML5, CSS3 and vanilla JavaScript only**. No backend, no build step —
just open `index.html` in a browser.

## Data Source

All timetable data in `data.js` was transcribed directly from the uploaded
`Timetable(1).pdf` (12 pages, one per section, Sections **A–L**). Nothing was
invented. Where the PDF itself contained an unclear, cut-off, or duplicated
entry (e.g. a repeated course code in two columns, or a partially printed
code), that record is tagged with a `verification` field reading **"Needs
Verification"** together with a short note describing exactly what was
ambiguous in the source document. These also render as an amber "Needs
Verification" badge in the UI.

Note: Section F's source page is dated for the 2025-26 academic year
(B.Tech CSE-BTIA, Year/Sem II/IV) while the other eleven pages are dated
2026-27 (Year/Sem III/V) — this is exactly as printed in the PDF.

## File Purpose

| File | Purpose |
|---|---|
| `index.html` | Landing page, role-aware login/create-password modal, the app shell (sidebar/topbar/content), the add/edit timetable-entry modal, and the confirm dialog. |
| `style.css` | All visual styling: landing page, sidebar navigation, dashboard cards, timetable grid, tables, modals, toasts, responsive breakpoints and print styles. |
| `data.js` | `PERIODS`, `DAYS`, `SECTION_META` and `timetableData` — the full dataset extracted from the PDF, plus a frozen `ORIGINAL_*` copy used by "Reset Data". |
| `auth.js` | The authentication & account-storage module: student self-signup, admin-created faculty accounts, the seeded Admin account, salted password hashing, and all account CRUD (create/reset/remove faculty accounts, change Admin password). |
| `script.js` | Everything else: session handling and login-form wiring, localStorage persistence, routing between views, rendering for Admin/Student/Faculty roles, global search, filters, conflict detection, add/edit/delete of timetable entries, reports and printing. |

## How the Files Connect

1. `index.html` loads `data.js` first (so the dataset exists globally as
   `timetableData`, `SECTION_META`, `PERIODS`, `DAYS`), then `auth.js` (which
   exposes `window.AUTH`), then `script.js`, which calls `AUTH` for every
   sign-up/login/account-management action and reads/writes the timetable
   data (backed by `localStorage` so admin edits survive a page refresh).
2. `script.js` renders all views into the `#pageContent` element inside
   `index.html` based on the signed-in role (Student / Faculty / Admin) and
   the currently selected sidebar item.
3. `style.css` is linked in the `<head>` of `index.html` and styles
   everything, including a dedicated `@media print` block used by the
   "Print Timetable" and "Print Report" buttons.

## Login & Security Model

Role is fixed by which card you click on the landing page (Student /
Faculty / Admin) — it is never a field a person can type or select in the
login form itself, so there's no "pick your role" dropdown to misuse.

- **Student** — Students create their own password once, using only their
  official college email (`@joyuniversity.edu.in`; every other domain is
  rejected). After that they log in with that email + password. There is no
  option anywhere in the Student UI to create a Faculty or Admin account.
- **Faculty** — Faculty never self-register. From **Admin → Faculty →
  Faculty Login Accounts**, the Admin picks a faculty member and the system
  generates a unique username and a one-time password to copy and send by
  email. Each faculty account is permanently bound to exactly one faculty
  member's name, so a logged-in faculty member only ever sees their own
  schedule — there's no picker that lets them browse anyone else's.
- **Admin** — A single Admin account is generated by the system the first
  time the app runs in a browser:
  - Username: `admin`
  - Password: `JoyAdmin@2026`

  This default password is a one-time bootstrap credential, not something
  meant to stay in use — the Admin is prompted to change it immediately
  from **Settings → Admin Account** the first time they log in. Students
  and Faculty have no page, link, or API call anywhere in the app that
  reveals the Admin username/password or the Admin dashboard.
- **Passwords** are never stored in plain text — each one is salted and
  hashed (`SHA-256` via the browser's Web Crypto API) before being written
  to `localStorage`.
- **Role separation in the UI** is structural, not just hidden buttons: the
  page router (`renderCurrentView` in `script.js`) branches on the signed-in
  role first, so a Student session can never render an Admin/Faculty view
  even if a matching view name were forced in some way, and every
  faculty-only page reads the faculty member's name from their own signed-in
  session rather than from any user-editable field.

**Important limitation, stated plainly:** this project is — and remains — a
front-end-only prototype with **no server/backend**. All accounts, password
hashes and sessions live in the browser's own `localStorage` /
`sessionStorage`. That's enough to stop normal use of the Student/Faculty/
Admin UIs from crossing role boundaries, but it is **not** the same as
server-enforced authorization: someone who opens their own browser's
DevTools console could still inspect or edit local values on their own
machine. A real deployment needs a backend that issues session tokens and
re-checks the caller's role on every request, independent of anything
running in the browser. Treat this implementation as the strongest
practical approximation of that for a class prototype — not as
production-grade security.

## Running the Project (VS Code)

1. Open VS Code.
2. Open the `college-timetable-management-system` folder (`File → Open Folder…`).
3. Confirm all five files (`index.html`, `style.css`, `script.js`, `data.js`,
   `auth.js`) and the `README.md` are present.
4. Double-click `index.html` in the file explorer and choose **"Open with
   Live Server"** (if you have the Live Server extension installed), **or**
   simply double-click `index.html` in your file system to open it directly
   in a browser — no server is required.
5. From the landing page, choose **Student**, **Faculty** or **Admin**:
   - **Student:** use "Create Password" once with a `@joyuniversity.edu.in`
     email, then log in with that email + password.
   - **Faculty:** log in with the username/password the Admin generated for
     you (see below).
   - **Admin:** log in with `admin` / `JoyAdmin@2026`, then change the
     password immediately in Settings.

## Key Features

- **Role-based login & dashboards** for Student, Faculty and Admin, each
  fully separated (see "Login & Security Model" above).
- **Section-wise timetable** for all 12 sections (A–L) with filters by
  department and section.
- **Faculty schedule lookup** — search or select any faculty member to see
  their full weekly schedule.
- **Classroom / Laboratory schedule** — pick a room or lab to see day-by-day
  occupied/available status.
- **Conflict detection** — automatically flags faculty double-booking, room
  double-booking, and a section having two subjects at once, based on actual
  time-range overlaps (not just matching period labels).
- **Global search** across section, subject, course code, faculty, room, day
  and time.
- **Working filters** everywhere they're listed, with department/section
  cascading.
- **Today's Classes** — computed live from `Date()`, including "Current
  Class" and "Next Class".
- **Admin CRUD** — add/edit/delete timetable entries through a modal form
  that runs conflict detection before saving and lets the admin proceed or
  cancel.
- **Reports** — section-wise, faculty-wise, room-wise and subject-wise,
  each printable via the browser print dialog (dedicated print CSS hides
  the sidebar/topbar/buttons).
- **localStorage persistence** for every admin change, with a **Reset Data**
  action (Settings) that restores the original PDF-derived dataset.
- **Fully responsive** — collapsible sidebar on tablet/mobile, horizontally
  scrollable tables and timetable grid, touch-friendly buttons and forms.

## Notes on Data Fidelity

- Codes printed inconsistently in the source PDF (for example a course
  listed as `24BTAM153` in the subject table but printed as `25BTAM153` in a
  schedule cell) are kept exactly as printed in that cell and marked
  **Needs Verification** rather than silently "corrected".
- A few schedule cells repeat the same course code twice in one day for one
  section (as printed in the PDF) — these are transcribed faithfully rather
  than assumed to be errors and de-duplicated.
- Section K's subject table lists `24BTCY157` for *Principles of Management*,
  while its printed schedule grid uses `24BTCY851` in those cells — both
  values are exactly as printed; the schedule cells are marked **Needs
  Verification** to flag the mismatch.
